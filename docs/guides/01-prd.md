# PRD 쓰는 법

PRD(요구사항 정의서)는 **무엇을, 왜** 만드는지 적는 문서예요. 멘토 말처럼 PRD가 틀리면 Spec과 코드가 다 틀려요. 그래서 코드보다 PRD에 시간을 더 써요.

## 문서 구조

- `docs/prd/00-root.md`: 전체 지도. 문제, 페르소나, 핵심 기능, 페이지 목록 링크만.
- `docs/prd/P01~P06`: 페이지마다 한 장. 한 사람이 한 페이지를 맡아요.
- 기능은 `P03-F02`처럼 ID를 붙여요. 브랜치, 커밋, PR, Spec, 테스트에 같은 ID를 써요. AI도 이 번호로 기능을 헷갈리지 않아요.

## 섹션 (모든 페이지 PRD 공통)

| 섹션 | 쓰는 것 | 흔한 실수 |
|---|---|---|
| 요약 | 이 페이지가 하는 일 2~3문장 | 기능 나열로 시작 |
| 왜 필요한가 | 회의, 멘토링, 조사에서 나온 근거 | 근거 없이 "편리하다" |
| 목표 | 사용자가 이 페이지에서 이루는 것 | 기술 목표 (빠른 로딩 등) |
| 하지 않는 것 | 이번에 안 만드는 것 | 비워 두기. AI가 멋대로 기능을 넣는 걸 막는 칸이에요 |
| 사용자 이야기 | "OO로서, OO하고 싶다" | 시스템 입장으로 쓰기 |
| 기능 요구사항 | ID, 기능, 설명, 범위 (MVP, 다음) 표 | 한 줄에 기능 여러 개 |
| 예외와 빈 상태 | 데이터 없음, 실패, 이상한 입력 | 성공하는 경우만 쓰기 |
| 데이터 | 어디서 오는지, 파일 경로, 기준일 | 출처 빼먹기 |
| 수용 기준 | Given, When, Then 문장 | "잘 동작한다" 같은 말 |
| 화면 | 캔버스 보드 이름, 프로토타입 주소 | 화면 없이 글로만 |
| 미결 사항 | 아직 못 정한 것, 담당 | 미결을 숨기기 |

## 만드는 순서

1. **맥락 모으기**: 관련 회의록 (`docs/meetings/`, `docs/notion/회의록/`), 조사 (`research/*/README.md`), 프로토타입 화면, 지금 PRD.
2. **AI로 초안**: Claude Code에서 `/prd-draft P03` (아래 명령어 참고). 맥락 파일을 `@`로 붙여요.
3. **사람이 읽고 고치기**: 아래 체크리스트로. AI가 쓴 문장은 그럴듯하지만 우리가 정한 것과 다를 수 있어요.
4. **화면으로 확인**: 프로토타입이나 캔버스를 보면서 PRD와 다른 곳을 찾아요. 다르면 둘 중 하나를 고쳐요.
5. **팀원 리뷰**: 다른 팀원 1명이 `/prd-review P03`으로 AI 리뷰를 받고, 직접 읽고 PR에 의견을 남겨요.
6. **버전 올리기**: 문서 맨 위 버전을 v1.0, v1.1처럼 올리고 맨 아래에 바뀐 점을 한 줄 적어요.

## 리뷰 체크리스트

- [ ] 우리가 회의에서 정한 것과 맞나 (특히 "합격 예측 안 함", "고르는 건 사용자")
- [ ] 하지 않는 것이 적혀 있나
- [ ] 기능마다 ID가 있고, 한 줄에 기능 하나인가
- [ ] 예외와 빈 상태가 기능마다 있나
- [ ] 수용 기준이 Given, When, Then으로 눌러서 확인할 수 있게 쓰였나
- [ ] 숫자마다 출처와 기준일이 있나
- [ ] 다른 페이지 PRD와 부딪히는 곳이 없나 (같은 데이터, 같은 버튼 이름)
- [ ] 미결 사항에 담당이 있나

## 좋은 예, 나쁜 예

| 나쁜 예 | 좋은 예 |
|---|---|
| AI가 경험을 분석해서 적합도를 알려준다 | P03-F02 공고 요구 문장마다 이력서에서 근거 문장을 찾는다. P03-F03 판정은 규칙으로: 같은 행동과 수치가 있으면 맞음 |
| 오류가 나면 처리한다 | AI 응답이 10초 넘게 없으면 "비교하지 못했어요. 다시 시도" 버튼을 보여 주고 이전 결과는 그대로 둔다 |
| 잘 동작해야 한다 | Given 이력서가 있는 사용자 When 비교하기를 누르면 Then 10초 안에 문장마다 표시가 생긴다 |
